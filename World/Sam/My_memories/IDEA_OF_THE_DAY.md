## Idea: Pact Provider State Injection Framework

Implement a `ProviderStateRegistry` in `bag/` that allows the Auth service to register setup hooks (e.g., `seed_user`, `clear_sessions`) mapped to specific state identifiers. These hooks will be exposed via a protected internal endpoint, allowing the Pact verification process to dynamically configure the service state before executing contract tests.

## Why
Currently, my contract testing strategy lacks a mechanism to ensure the provider is in the required state (e.g., "User X exists") without polluting the production database or relying on brittle, pre-existing data. This framework ensures isolation and determinism, which are critical for the "Contract Testing Diamond" pattern.

## Implementation Steps
1.  **Create `bag/provider_states.py`:** Define a `StateRegistry` class with a decorator `@register_state("state_name")` to map strings to setup functions.
2.  **Expose Internal Endpoint:** Add a `POST /_pact/state` endpoint to the Auth service that accepts a JSON payload `{"state": "..."}` and executes the corresponding registered function.
3.  **Update Verification Logic:** Modify the Pact verification script to call this endpoint as part of the `provider_states` configuration in the Pact test suite.
4.  **Security:** Ensure the endpoint is only accessible when `ENV == 'testing'`.

## Risk
**Failure Mode:** The state injection endpoint could be accidentally exposed in production, allowing external actors to trigger database seeding or clearing.
**Mitigation:** Implement a hard-coded check in the endpoint that verifies the environment variable `SAM_TESTING_MODE` is set to `true` and that the request originates from `localhost`.
